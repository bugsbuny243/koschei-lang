# Koschei Lang — Monthly Security-Language Intelligence

**Window:** 2026-09-06 → 2026-10-05  
**Compiled:** 2026-10-06

## Design principle

Do not hard-code transient MCP/IETF/vendor wire formats into the language core. The month’s research consistently favors **protocol-neutral security semantics** with adapters at the library/runtime boundary.

## Strong language-level abstractions suggested by the month

### 1. Trust and state progression

Keep these states distinct:

`UntrustedObservation<T> → VerifiedObservation<T> → CanonicalState<T> → AuthorizedState<T> → ExecutableEffect<T> → EffectReceipt<T>`

Motivation: Long Bridge/non-canonical RPC, cross-chain finality, agent tool results and protocol activation state all show that external observation is not automatically canonical/executable state.

### 2. Identity is not authority

Separate concepts such as:

- `IdentityCredential`
- `OwnerBinding`
- `CapabilityClaim`
- `DelegatedAuthority`
- `ScopedAuthority`
- `FreshnessWitness`
- `RevocationState`
- `ActionAuthority`

Motivation: agent registry/AINS/AIRS/X.509/AAuth/OAuth research repeatedly separates discovery, identity, delegation and current action authorization.

### 3. Proposal is not execution

Model effect phases separately:

`Observe → Propose → Simulate/DryRun → Authorize → Execute → VerifyEffect`

Receipt-gated effectuation further suggests:

`BoundedEffect₀ → Receipt₀ → Validate → ContinuationAuthority → Effect₁`

This should be an effect/authority abstraction, not MCP-specific syntax.

### 4. Protocol/capability lifecycle

Represent lifecycle explicitly rather than boolean support:

`Declared → Implemented → Deployable → Activated → Observed → Finalized/Usable → Deprecated/Paused`

Motivation: Solana/Alpenglow, Zcash NU7, THORChain/ZEC, Arbitrum Stylus and multiple IETF draft lifecycles.

### 5. Artifact identity continuity

Dependency/runtime contracts should be able to bind:

`requested → resolved → materialized → provenance-verified → runtime-loaded`

Motivation: Plugin4Shell and broader agent/plugin supply-chain research. Reviewed package identity must match executed artifact identity.

### 6. Crypto agility

Avoid a single hard-coded signature/KEM/hash suite. Use provider/policy abstractions for:

- Signature
- KEM
- Hash
- Commitment
- Proof / ZK backend
- Key lifecycle
- Trust anchor
- Crypto policy/profile

Support Classical / Hybrid / PostQuantum providers without changing application semantics.

Research drivers: Ethereum PQ roadmap, Cloudflare hybrid TLS, Quantus/Tezos Quantumnet/other PQ-chain experiments, Zcash Epoch, Java/runtime PQ migration, NIST/ETSI work and PQ agent-identity requirements.

Critical rule: a PQ leaf credential under a classical trust anchor is not end-to-end PQ authority.

### 7. Evidence semantics

Do not treat all signed objects as one `Proof` type. Distinguish:

- identity evidence
- authority evidence
- state/finality witness
- execution receipt
- outcome/effect evidence
- provenance record
- audit record
- formal-verification evidence

A signed/tamper-evident receipt may prove only that a system recorded a claim, not that the claimed external effect is true or safe.

### 8. Privacy properties

Separate:

- `PaymentAuthority`
- `ContentDisclosure`
- `NetworkDisclosure`
- `UsageReceipt`
- unlinkability/anonymity properties

Motivation: zkAPI showed payment unlinkability does not imply network/content anonymity.

## Candidate library/runtime contracts (conceptual, not syntax commitment)

- `verify_observation(source, witness) -> VerifiedObservation<T>`
- `establish_canonical_state(observations, finality_policy) -> CanonicalState<T>`
- `attenuate(authority, scope) -> ScopedAuthority`
- `bind_authority(authority, state, intent) -> ActionAuthority`
- `execute(action_authority, effect) -> EffectReceipt<T>`
- `reconcile(receipt, observed_state) -> VerifiedEffect<T>`
- `crypto_provider(policy) -> CryptoProvider`
- `verify_artifact(provenance, materialized_artifact) -> VerifiedArtifact`

Names are placeholders; semantics matter more than syntax.

## Threats to avoid in Koschei Lang design

- Treating authenticated identity as action authority.
- Treating signed evidence as truth.
- Treating network/transport success as effect success.
- Treating testnet/deployed code as activated production capability.
- Baking one PQ algorithm into the language.
- Accepting classical fallback silently during PQ migration.
- Loading a dependency different from the reviewed/resolved artifact.
- Turning untrusted external/RPC state directly into executable state.
- Binding language semantics to short-lived Internet-Drafts or vendor protocols.

## Standards/Web4–Web8 conclusion

No universal W3C/IETF Web4–Web8 generation standard was found in this month. WebMCP, agent identity/delegation/evidence protocols and other drafts are useful interoperability inputs but should remain replaceable adapters until their status and deployment mature.

Recommended status model:

`RFC/W3C Recommendation → WG draft → individual I-D → Community Group/incubation → research/vendor proposal → implementation → production deployment`

## Design objective

Koschei Lang should make unsafe authority/state transitions difficult to express by default while remaining crypto-agile and protocol-neutral. The strongest recurring design direction from the month is:

**untrusted data must become verified state; verified state plus scoped/fresh authority may become executable state; execution must return evidence that can be reconciled against the resulting state.**
